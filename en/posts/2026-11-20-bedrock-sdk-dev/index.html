The story of building the entire Mod development environment for Minecraft Bedrock | The true cause of SDK, automated testing, and device crashes

Conclusion first

  • We built and operate an SDK from scratch for creating client Mods for Minecraft Bedrock (Windows edition).
  • We implemented a mechanism for tracking game updates using "signature scanning + differential prediction."
  • Testing involves setting up an environment on Linux to run the Windows version of the game headless and unattended, and utilizing an AI agent.
  • The biggest challenge was crashes that only occurred on physical hardware, and the root cause was that "the Mod's runtime was freeing memory allocated by the game's allocator."

Why build a custom SDK

Official Bedrock client mod mechanisms are centered around server-side script APIs, meaning penetrating client-side drawing or input requires injecting a native DLL. While there are several existing SDKs, I decided to build my own, prioritizing fast version tracking and the API structure I want.

The current SDK searches for function addresses by version using "signatures" (machine code patterns). Even if the game is updated, it can automatically track changes if the pattern remains.

Version Tracking Mechanism

When a new version is released, what needs to be done is decided.

  1. Scan the new version's executable using the surrounding byte sequences of addresses known from the old version to find candidates.
  2. For those not found, predict the correct address based on the movement (delta) of nearby functions.
  3. Once all symbols are resolved, inject them and confirm functionality.

For the most recent version compatibility, all 74 symbols were ported using this procedure. It's subtle, but we are freed from "constantly staring at disassembly by hand." There are pitfalls, such as list-format address values being missed during scalar value rearrangement, or profile cache taking precedence over embedded data, leading to the situation where "it doesn't work even though I fixed it"; these are documented in the procedure manual.

Automated Testing Environment: Running Windows version unattended on Linux

Since manually verifying Mod operation every time is limited, I also created a testing environment.

  • Launching Windows version Bedrock via a compatibility layer on a Linux machine and running headless with a virtual display
  • Scripting everything from DLL injection, server joining, executing commands via chat, to capturing screen screenshots
  • Setting up a verification Bedrock server (BDS) on the same hardware allows unattended confirmation of a sequence of actions, such as joining, mining, and crafting

This allows me to fully delegate "fix, test, and leave evidence" to an AI agent. The operation is that humans just wake up in the morning and read the results.

However, even if automated tests pass, it can crash on the actual hardware. The next topic is about that.

The true cause of the crash that only occurred on the actual machine

There was an issue where a certain Mod would always crash immediately after command execution on the actual Windows machine, but not reproduce in the automated testing environment (on a compatibility layer).

The true cause was crossing memory allocators. When an internal game function "returns an array of elements," that memory is allocated by the game's allocator. If the Mod's C++ runtime frees it normally, the heap gets corrupted and crashes. On the compatibility layer, it simply didn't surface, but on the actual machine, it was a landmine that guaranteed failure.

The solution was to copy the contents of the returned array into a custom array and have the original buffer returned using the game's release function. This lesson—that "ABIs returning containers via hidden return values are all landmines"—was applied to all functions of the same form.

The lesson is simple: passing automated tests and running on the actual machine are separate things. Therefore, we still perform final checks on the actual machine and do not state that automated test results "are proven on the actual machine."

What I am currently working on

The SDK is currently undergoing a complete overhaul, abandoning compatibility. The highlight is a plugin system where Mods can be written in TypeScript; the goal is that injecting a single DLL makes it a host, and Mods placed in a folder are automatically loaded. We are also progressing on adding custom items to the settings screen (mixing Mod settings into the game's settings UI) and official API implementation for key assignments.

Summary

  • Following version updates is faster if it is systematized. The personalized reverse assembly work has been proceduralized.
  • The automated testing environment is powerful, but there are always issues that only appear on actual hardware. Consider this as a separate premise.
  • You must not free another person's allocator memory (obvious, but I mentioned it).
