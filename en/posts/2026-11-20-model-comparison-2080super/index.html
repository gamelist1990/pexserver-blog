How many tok/s is achieved when changing models on the same RTX 2080 SUPER | Measured comparison of Gemma 4 E4B, Qwen 35B, and Ornith 35B

Conclusion First

  • After swapping models on the same RTX 2080 SUPER (8GB VRAM), the model currently running in production is Gemma 4 E4B (generation approx 113 tok/s, parallel 3)
  • 35B class models like Qwen3.6-35B-A3B / Ornith-1.5-35B-A3B fall below 60 tok/s in generation. For prefill only, Qwen was the fastest at about 1,174 tok/s
  • The deciding factor for speed was not the number of parameters, but the number of quantization steps, how MoE was implemented, and the presence of MTP (speculative decoding)
  • 2-bit quantization came with a trade-off. Context collapse of history is occurring in practical operation

Previously, I wrote about "How a mini PC + used eGPU made local LLMs practical." This is a continuation, summarizing the actual measurements from testing various models on the same hardware.

Disclaimer: Not a strict identical condition benchmark

All numbers are measured results from my own environment. However, the measurement timing, engine, parallel count, and context length vary by model. Specifically, Qwen / Ornith were measured using the MoE dedicated engine (RustingStrata), and the Gemma series was measured using the CUDA version of llama.cpp. Therefore, please read this table not as a "benchmark ranking list," but as a record of "what happened when I actually operated it on the same GPU and on the same desk."

Why E4B is production

The bot handles 3 requests simultaneously. E4B maintains generation of approximately 113 tok/s even with 3 parallel streams. 35B class drops below 60 even with a single stream, and drops further when parallelized. What determines the user experience of a chat bot is the generation speed (returning one token at a time), rather than prefill, which processes long inputs all at once. Even if Qwen wins at prefill, it was meaningless if the response was slow.

The order tried was E4B → Qwen 35B → Ornith 35B → E4B (current). The flow was switching to a larger model, but returning due to speed and stability.

Why 35B is slow: The 8GB VRAM wall

Qwen3.6-35B-A3B uses MoE (mixture-of-experts) and is designed to load only the necessary experts into VRAM. Even so, the file is 10.68GB in IQ2_XXS, and VRAM usage was approximately 7,134MiB, nearly reaching the limit.

If I tried to increase the quantization level, IQ2_XS is 11.69GB, IQ3_XXS is 15.76GB, and Q4_K_M is 22.29GB—none of them fit into 8GB. The overflow is offloaded to system RAM (which is single-channel DDR5, approximately 45GB/s). In the precedent of Gemma 26B's CPU-MoE offload, prefill dropped to about 360 tok/s. In other words, increasing the quantization for Qwen was almost the same as giving up the "prefill over 1,000" motivation for switching to Qwen.

Given the choice between "increasing quantization" or "returning to E4B," I chose to return to E4B.

The Cost of 2-bit Quantization: Context Collapse of History Occurred

During the operation of Qwen IQ2_XXS, a real-world operational issue occurred on 2026-11-11. The Bot repeated its previous statements or fabricated completion reports, claiming "done!" for drawing tools that were not executed. Troubleshooting revealed that the Bot side and the API path were normal; the cause was the model itself. The 2-bit quantized model completed the conversation history patterns as if they were "continuations of a script."

As a countermeasure, since adding the rules "history is not a script" and "completion reports for unexecuted tasks are prohibited" to the Bot's prompt, it has not recurred. However, the root cause is the weakness of quantization. The lesson learned from real-world operation is that it is dangerous to jump to 2-bit just by looking at speed metrics.

The story that tweaking settings didn't improve performance

On the Strata side, 512 was optimal for the expert cache amount (--cache-ram), and increasing it to 3,072 significantly degraded generation from 66.8 → 27.5 tok/s. Power limit 200W → 250W, chunk 6144 → 8192, and threads 12 → 16 also did not exceed the same range of approximately 860~890 tok/s, remaining within the margin of error.

In short, there is almost no room to tweak settings with this configuration. The conclusion is that if you want it faster, you must change how you choose the model.

Summary: How to choose with 8GB VRAM

  • For chatbot use where generation speed is critical, smaller models + good quantization + MTP outperformed larger models + 2-bit quantization
  • For use where prefill is critical (reading long texts all at once), Qwen 35B's 1,174 tok/s is attractive. The model chosen depends on the use case.
  • If running 35B class models on 8GB, IQ2_XXS is the limit for quantization; anything higher loses speed due to offloading.

Next, I want to re-measure Nemotron 3.5 Bolt E4B on CUDA, which improves agent performance based on the same Gemma 4 E4B foundation. If it gets smarter without sacrificing speed, it will be a candidate to replace the current model in production. I haven't measured it yet, so I will write again when I have the results.
